## 两种正式接入选择

| 选择                     | 优点                                                               | 前提与代价                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 原生独立回调函数（建议） | 复用已跑通的云函数推送，不需要新域名、HTTP路由或微信消息加解密配置 | 仅接收函数长期允许调用；依赖平台实际运行上下文及SDK来源校验。普通攻击请求虽不能批准照片，仍可能消耗调用额度，不能宣称零成本或零滥用风险 |
| 保留签名HTTP接收         | 保留现有验签、解密与业务能力对象设计，认证不依赖客户端给出的字段   | 仍缺已确认的生产HTTPS地址、备案域名、消息推送配置及完整入口适配。不得擅自购买，默认测试域名也不冒充可靠生产地址                         |

不采用“只检查event.TCB_SOURCE”或“提交成功即批准”的第三条捷径；它们与实测或业务安全要求冲突。也不通过删除图片能力来缩小正式版目标。

## 推荐方案的固定边界

1. 新建独立的mediaSafetyCallback，仅承接event/wxa_media_check，不将现有临时mediaSafetyProbe改为生产入口，避免恢复脚本覆盖业务。接收器不接受action路由，不上传、下载或返回照片，不提供客户端批准接口。
2. 来源必须同时由实际handler第二参数和初始化后的服务端SDK确认；AppID及环境必须由SDK提供并匹配预期值。实际上下文若也提供WX_APPID、TCB_ENV或SCF_NAMESPACE，必须一致，不能用缺少SDK字段的上下文作替代。缺来源、冲突或非法形状均拒绝。不从event、event.context、tcbContext、userInfo、HTTP头或调用者提交的SOURCE取得认证。
3. 明确验证v2事件、应用、trace_id、有限审核状态和大小上限后，才在服务端创建不可通过JSON克隆恢复的已认证能力对象。外部结果不能只靠suggest=pass进入现有事务服务。
4. 复用已完成的uploadedFiles与mediaAuditEvents事务：任务、上传者、用途及文件固定绑定；提前回调先保存受完整性保护的收件记录，再按真实任务绑定。重复幂等、冲突阻断，未知任务不能批准任何文件。
5. 原生模式不需要微信HTTP回调Token/AES配置，但现有持久化证明使用AES密钥作MAC，因此必须显式分离认证模式与服务端完整性密钥。使用独立的32字节服务端完整性密钥，不复用AppSecret或OCR凭据，不写入客户端、仓库、日志或工单。两端配置一致后才启用；无配置不自动回退或放行。
6. 保留HTTP模式及其原验签测试，使用显式配置选择接收模式，不把任一普通对象同时当成两种来源的已认证结果。若线上已有审核记录或旧证明，必须先只读核实，再决定兼容策略，不能直接换钥使历史批准失效。
7. 仅该生产回调函数需要精确的长期invoke规则；通配拒绝、api及其他函数规则不放宽，诊断函数保持关闭。规则、推送绑定、新代码和恢复路径逐项回读；生产切换不是此前临时测试授权的自动延续。
8. 学生端待审核、复核、拒绝、错误、超时及旧照片隔离保持原样。只有服务端最终通过且用途、文件和角色检查通过才允许引用或签发短时地址。真机验收仍单独待办。
